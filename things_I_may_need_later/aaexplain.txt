Writing this kind of backward, but here's what's going on.  I made a complete character set in svg. 
I spent a lot of time tuning each character so that it lined up nicely, and all the characters, 
which were individual svg paths, appeared to be a unified character set. 

When I displayed them on the screen, I displayed them using a use with x and y coordinates attached. 
(The paths were defined earlier in a def section)  The paths, as they came out of the tool (see 
Abe_google-font-to-svg-path) were defined absolutely.  And I added transforms to line them up. 
As they came out of the tool, each path was crowded to the top of its character box. 

The idea was, that if I defined the paths relatively, I would be able to put the characters out there 
wherever they should go, and wouldn't have to specify x,y coordinates.  And if I inserted a character, 
the coordinates of cells on the right wouldn't have to be changed.  Mostly, the concern was responding 
quickly as a person typed. 

But that relies on a misconception.  If the cell on the left ends up on the pixel one to the right 
of its top right pixel, and the cell on the right assumes it starts at its top left pixel, that doesn't 
result in the cell on the right appearing to the right of the cell on the left.  They end up on top 
of each other. 
Each path is independent.  Even if the previous cell ends up in the right position, it has no 
effect on the following cell.  (And who said the cells would be painted in left to right order?)

So the whole scheme fails.  Grok says modern processors are so fast, that updating all the cells 
to the right is no problem.  That may be true.  We'll see. 

But I thought I should preserve the work.  It may be useful later. 
Anyway, it shows how to merge a transform into the coordinates themselves.  And how to 
transform a set of absolute coordinates into a set of relative coordinates. 

So there's normalize_glyphs_v1.go, normalize_glyphs_v2.go, and normalize_glyphs.go. 
We went through a couple of iterations before arriving at the final program.

Updated full procedure (now complete)

For every glyph in character-definitions.html:

    1. Read the old transform="translate(tx, ty)" on its <g>.
    2. Bake those values into the path data (add tx to every X number, ty to every Y number). This is 
	   exactly what we discussed before.
    3. Convert the now-baked absolute path to relative form:
        a. Keep a running currentX, currentY (start at 0,0 for the cell).
        b. First M x y → m x y (relative move from wherever you place the glyph).
        c. Every subsequent absolute point → compute delta from previous current point, output lowercase command 
		   (l, q, a) with the deltas, update current.
        d. Z stays z (closePath).
        e. A arcs become a with the same rx/ry/rotation/flags but dx dy endpoint delta.
    4. After the last command of the glyph (including any z), append one final relative move: m 8 0.
	   This guarantees the current point ends at (8, 0) relative to the cell origin — exactly the top-left 
	   of the next cell.

Result: every character is now a self-contained relative path that:

    1. Draws itself correctly positioned inside its 0–7 × 0–15 cell (because we baked the old visual offsets), and
    2. Leaves the pen at +8 in x so the next character starts in the right place with zero extra code.

Okay, I talked to Grok again.  It was incredibly hard to make him see the point 
(you have to really stick with your guns with Grok) but eventually he said that 
his code was wrong.  You can't just append m 8 0 at the end of any glyph drawn 
using relative motions, and expect the resulting position to be the upper left 
corner of the next character cell.  That only works if the glyph ends with 
z or Z.  

He made a new version of the program, so I designated the former "new version" 
as v3. 

Here is part of what Grok said to me: 

      Why blindly appending m 8 0 is insufficient

As you correctly pointed out, m 8 0 only moves +8 from wherever the current point happens to be. 
If the glyph didn’t leave the current point at (0,0), then m 8 0 will not land at (8,0) relative to the origin.

Better implementation in toRelative()

The cleanest fix is to change the end of toRelative() so that instead of always doing:
Go
out = append(out, Command{Cmd: 'm', Args: []float64{8, 0}})

We do something like:
Go
// After processing all the glyph's commands, force the current point to (8, 0)
dx := 8 - curX
dy := 0 - curY
out = append(out, Command{Cmd: 'm', Args: []float64{dx, dy}})

This keeps everything relative while still achieving your desired behavior: each glyph segment 
leaves the current point at the top-left of the next cell.

The transform="translate(...)" on the <g> inside <defs> is not evaluated only once at definition time.
